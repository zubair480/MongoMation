## 0. TL;DR: the minimal correct integration [PKG][TSC]

```bash
npm install raindrop-ai@1.0.1          # OTel v2 apps: npm install raindrop-ai@otelv2
npm install @raindrop-ai/query@0.1.14  # only for reading data back (RSI meta-agent)
```

```ts
import { Raindrop } from "raindrop-ai";        // `import Raindrop from "raindrop-ai"` also works
import { randomUUID } from "node:crypto";

const raindrop = new Raindrop({ writeKey: process.env.RAINDROP_WRITE_KEY! }); // SDK does NOT read the env var itself

const eventId = randomUUID();                     // pre-generate -> store in MongoDB as evidence
const interaction = raindrop.begin({ eventId, event: "plc_job", userId: "mongomation-worker",
  convoId: jobId, model: "claude-sonnet-4-5", input: prompt, properties: { job_id: jobId } });

const sim = interaction.startToolSpan({ name: "run_simulation", inputParameters: { suite: "smoke" } });
try { const r = await runSim(code); sim.setOutput(r); if (r.failed.length) sim.setError(`${r.failed.length} tests failed`); }
catch (err) { sim.setError(err instanceof Error ? err : String(err)); }
finally { sim.end(); }

await interaction.finish({ output: "2/10 sim tests failed after 3 repairs" }); // non-empty output!
raindrop.trackSignal({ eventId, name: "sim_tests_failed", sentiment: "NEGATIVE", properties: { failed: 2, total: 10 } });
await raindrop.close();                            // REQUIRED in short-lived processes
```

## 3. TypeScript SDK (`raindrop-ai`) [PKG][TSC]

### 3.1 Constructor options (`AnalyticsConfig`, all optional)

| Option | Meaning |
|---|---|
| `writeKey` | Ingest key. Required for cloud ingest. |
| `apiKey` | Query SDK org key. Only for evals, datasets and replay; never used for ingest. |
| `projectId` | Project slug, sent as the `X-Raindrop-Project-Id` header. |
| `endpoint` | Default `https://api.raindrop.ai/v1/`. |
| `debugLogs` | Logs queued and sent events. Turn on during setup. |
| `disabled` | No-op client, for tests. |
| `redactPii` | Client-side PII redaction. |
| `bufferSize` | Default 50 events. |
| `bufferTimeout` | Default 1000 ms batch flush. |
| `maxTextFieldChars` | Default 1,000,000. Truncated fields end in `...[truncated by raindrop]`. |
| `bypassOtelForTools` | Ship tool/task spans via direct HTTP instead of OTel. This **also makes `withTool`/`withSpan` record thrown errors**; see 3.5. |
| `useExternalOtel` | Use your own NodeSDK or Sentry with `raindrop.createSpanProcessor()` and `raindrop.getInstrumentations()`. |
| `instrumentModules` | `{ openAI, anthropic, cohere, bedrock, google_vertexai, google_aiplatform, pinecone, together, langchain, llamaIndex, chromadb, qdrant, mcp }` |
| `disableBatching` | Default true when `NODE_ENV !== 'production'`. |
| `awaitSpanFlush` | Default true: `finish()` awaits the span flush. |
| `localWorkshopUrl` | `string`, or `false` to opt out of Workshop mirroring. |
| `appGit` | `{ commitSha, commitDirty, branch, detectBranch, sourceDirectory, autoDetect }`, or `false`. |

### 3.2 Public methods (complete list from the `.d.ts`)

On the `Raindrop` client:

- `begin(ctx): Interaction`
- `trackAi(ev | ev[]): string | (string|undefined)[] | undefined`
- `trackSignal(sig | sig[]): void | void[]`
- `selfDiagnose(opts): void`
- `setUserDetails({ userId, traits? }): void`. This is "identify".
- `resumeInteraction(eventId): Interaction`
- `tracer(globalProps?: Record<string,string>): Tracer`, with `withSpan`, `trackTool` and `emitLiveEvent`
- `asCurrent(fn)`
- `createSelfDiagnosticsTool(opts?)`
- `createSpanProcessor()`, `getInstrumentations()`
- `resumeSubagent(headers)`, `withSubagentRun(headers, fn)`
- `forceFlush(): Promise<void>`, `close(): Promise<void>`

There is **no** `track()`, and `flush()` is private.

On `Interaction`:

- `withSpan`, `withTool`, `startSpan` (returns a raw OTel `Span`), `startToolSpan`, `trackTool`
- `setInput`, `setProperty`, `setProperties`, `addAttachments`, `setFeatureFlag`, `setFeatureFlags`
- `finish({ output, ... }): Promise<void>`, `getEventId()`
- `vercelAiSdkMetadata()`, `emitLiveEvent`, `subagent(...)`

### 3.3 Single-shot `trackAi`

```ts
const eventId = randomUUID();
const ret = raindrop.trackAi({
  eventId,                                 // optional; SDK uses crypto.randomUUID() if omitted
  event: "plc_codegen",                    // REQUIRED, non-empty
  userId: "mongomation-worker",            // REQUIRED, non-empty (otherwise dropped with console.warn)
  convoId: jobId,
  model: "claude-sonnet-4-5",
  input: prompt,                           // input and/or output REQUIRED
  output: stCode,
  properties: { job_id: jobId, attempt: 1, phase: "generate" },   // nested JSON allowed
  attachments: [{ type: "code", language: "st", name: "Main.st", value: stCode, role: "output" }],
  usage: { provider: "anthropic", inputTokens: 1200, outputTokens: 800 }, // cacheRead/Write, reasoning, providerReportedCost optional
  // featureFlags: { harness_version: "v3" },  timestamp: ISO string
});
if (typeof ret !== "string") throw new Error("raindrop rejected the event (see debug logs)");
```

- **Synchronous.** The call buffers the event and returns its id. The buffer flushes every 1 s or at 50 events, via `POST /v1/events/track`.
- **Validation failures return `undefined`.** The zod schema is `.strict()`, so unknown top-level keys, an empty `userId`, or a missing input/output all cause this. The only report is a `console.warn`.

### 3.4 `begin()` / `finish()` (recommended)

```ts
const eventId = randomUUID();
const interaction = raindrop.begin({
  eventId, event: "plc_job", userId: "mongomation-worker", convoId: jobId,
  model: "claude-sonnet-4-5", input: prompt,
  properties: { job_id: jobId, harness_version: "v3" },
  featureFlags: { harness_version: "v3", repair_strategy: "diff" },  // cohorts for Experiments
  // tools: [{ name, description, parameters }]  // override recorded ai.prompt.tools catalog
});
interaction.setProperties({ compile_ok: false, sim_failed: 2 }); // custom metadata only
interaction.setProperty("final_status", "failed");
await interaction.finish({ output: "2/10 simulation tests failed after 3 repair attempts",
                           model: "claude-sonnet-4-5",
                           usage: { provider: "anthropic", inputTokens: 10, outputTokens: 5 } });
```

- **`eventId` is required by the TypeScript type** (`PartialAiTrackEvent`). At runtime it would be auto-generated, but in TypeScript you must pass it.
- **Set AI data only in `begin()`, `finish()` or `trackAi()`.** That covers `model`, `input`, `output` and `convoId`. `setProperty('model', ...)` does NOT set the model badge [GH].
- **Wire protocol:**
  - `begin()` immediately buffers a partial event with `is_pending: true`. Updates are debounced and flushed after 2 s idle to `POST /v1/events/track_partial`.
  - `finish()` sends `is_pending: false`, waits for earlier POSTs for the same event, and by default also awaits the span flush.
  - Partials with the same `event_id` are merged server-side.
- `raindrop.resumeInteraction(eventId)`:
  - In the same process, it returns the live interaction.
  - Otherwise it returns a fresh interaction that only knows `eventId`. Its updates and `finish` still merge server-side by event id.

### 3.5 Spans, tool calls, and **failed tools**

```ts
// task span (LLM calls made inside are auto-attached when instrumented)
const stCode = await interaction.withSpan({ name: "generate_st", properties: { attempt: "1" } }, // props: Record<string,string>!
  async () => generate(prompt));

// wrap a tool (success path)
const compiled = await interaction.withTool({ name: "compile_plc", inputParameters: { file: "Main.st" } },
  async () => compile(stCode));

// real-time tool span with explicit failure  <-- use this for failures
const sim = interaction.startToolSpan({ name: "run_simulation", inputParameters: { suite: "smoke" } });
try {
  const r = await runSim(stCode);
  sim.setOutput(r);
  if (r.failed.length > 0) sim.setError(`${r.failed.length} sim tests failed: ${r.failed.join(", ")}`);
} catch (err) {
  sim.setError(err instanceof Error ? err : String(err));   // catch var is `unknown`: must narrow
} finally {
  sim.end();                                                 // required
}

// retroactive tool record (already finished / timed externally)
interaction.trackTool({ name: "deploy_plc", input: { target: "sim-plc-1" }, durationMs: Date.now() - t0,
  error: err instanceof Error ? err : String(err), properties: { stage: "deploy" } });

// spans not tied to an event (batch jobs)
raindrop.tracer({ job_id: "batch-1" }).trackTool({ name: "nightly_regression", input: { n: 50 }, output: { failed: 3 }, durationMs: 9000 });
```

**Failure semantics, verified in the compiled source.** The two settings behave differently for a tool or task that throws:

- **Default OTel mode:** `withTool`/`withSpan` re-throw, but the span is only `end()`ed. **It is NOT marked `ERROR` and gets no exception recorded.**
- **`bypassOtelForTools: true`:** a throw inside `withTool`/`withSpan` is shipped with `error`.

These three paths record failure reliably in both modes:

- `startToolSpan().setError()` (OTel `SpanStatusCode.ERROR` plus `recordException`)
- `trackTool({ error })`
- `bypassOtelForTools: true`

Failure status in Raindrop is derived from errored spans (README: "a run with final output and no errored span reads as finished").

### 3.6 Attachments (code, diffs, logs)

```ts
interaction.addAttachments([
  { type: "code", language: "st",   name: "Main.st",     value: stCode,  role: "output" },
  { type: "code", language: "diff", name: "repair.diff", value: diffText, role: "output" },
  { type: "text", name: "compiler_log", value: log.slice(0, 50_000), role: "input" },
]);
```

- The shape is `{ type: "code"|"text"|"image"|"iframe", value: string, role: "input"|"output", name?, language? (code only), attachment_id? }`. The SDK only accepts `role` input/output; the HTTP doc also lists "context".
- `image` and `iframe` take a URL in `value`.
- Attachments can also be passed to `trackAi`/`begin` as `attachments: [...]`.
- `attachment_id` lets a signal target a specific attachment via `attachmentId`.
- Whether the UI syntax-highlights `language: "st"` is **[UNVERIFIED]**.

### 3.7 Signals (feedback, custom, eval results, self-diagnostics)

```ts
raindrop.trackSignal({ eventId, name: "sim_tests_failed", sentiment: "NEGATIVE",
                       properties: { failed: 2, total: 10, suite: "smoke" } });                     // type defaults "default"
raindrop.trackSignal({ eventId, name: "thumbs_down", type: "feedback", comment: "Interlock wrong", sentiment: "NEGATIVE" });
raindrop.trackSignal({ eventId, name: "operator_fix", type: "edit", after: "PROGRAM Main ... END_PROGRAM" });
raindrop.trackSignal({ eventId, name: "eval_pass_rate", type: "agent", sentiment: "NEGATIVE", properties: { score: 0.8 } });
raindrop.selfDiagnose({ eventId, description: "Simulator timed out on 3 retries",
                        category: "repeatedly_broken_tool", source: "mongomation" }); // -> signal "self diagnostics - <category>", type "agent"
```

- **Shape:** `{ eventId, name, type?: "default"|"standard"|"feedback"|"edit"|"agent"|"agent_internal", sentiment?: "POSITIVE"|"NEGATIVE", properties?, timestamp?, attachmentId?, comment? (feedback), after? (edit) }`.
  - It is sent to `POST /v1/signals/track`.
  - The HTTP spec says `feedback` requires a non-empty comment and `edit` requires `after`.
  - The SDK omits `sentiment` unless you set it. The docs table says it defaults to NEGATIVE, so set it explicitly.
- **Eval results:** there is no dedicated "eval result" signal API. Either send a custom instrumented signal (above), or use Raindrop Evals (section 5.4). Instrumented signals do not count against signal slots [DOCS-S].
- **Agent-callable reporting tool:**
  - Create it with `raindrop.createSelfDiagnosticsTool({ eventId | interaction | getEventId, signals?, guidance?, toolName? })`.
  - It has `.forAnthropic()`, `.forOpenAI()` and `.forVercelAI()` adapters, plus `.execute(input)`.
  - Default tool name: `__raindrop_report`.
  - Default categories: `missing_context`, `repeatedly_broken_tool`, `capability_gap`, `complete_task_failure`.

### 3.8 Event IDs as MongoDB evidence

- **Always mint the id yourself** (`crypto.randomUUID()`), write it to Mongo, then pass it as `eventId` to `begin`/`trackAi`.
- `interaction.getEventId()` and the return value of `trackAi()` echo it back.
- The HTTP API is idempotent on `event_id` [GH].
- The trace id is not exposed on the public `Interaction` type; `finish()` sets it as event property `trace_id`. Use the `eventId` to fetch traces: Query `traces.list({ eventId })` or MCP `get_trace({ event_id })`.

### 3.9 Flushing and shutdown

- **`await raindrop.close()` before a short-lived process exits.**
  - It drains the standard buffer and pending partial events.
  - It runs under a 10 s deadline, and after that payloads are dropped with a warning.
- **`await interaction.finish(...)`.** It is a Promise; awaiting it guarantees the terminal POST.
- `raindrop.forceFlush()` is a best-effort mid-run drain.
- Serverless: flush before returning [GH].

### 3.10 Limits

- 1 MB per event (`MAX_INGEST_SIZE_BYTES`). Text fields are capped at 1,000,000 chars by default.
- Attachments count toward the event size.
- `OTEL_SPAN_ATTRIBUTE_VALUE_LENGTH_LIMIT` is honored for span content.
- All HTTP calls have timeouts and are retried up to 3 times.

### 3.11 Raw HTTP ingest (fallback) [GH]

- Base URL `https://api.raindrop.ai/v1/`, with headers `Authorization: Bearer <writeKey>` and optionally `X-Raindrop-Project-Id`.
- **`POST events/track`** takes an array of `{ event_id, user_id, event, timestamp?, ai_data: { model?, input?, output?, convo_id? }, properties?, attachments? }`.
- **`POST events/track_partial`** takes a single object with `is_pending`.
- **`POST users/identify`** takes `[{ user_id, traits }]`.
- **`POST signals/track`** takes `[{ event_id, signal_name, signal_type, sentiment?, properties?, timestamp?, attachment_id? }]`.
- **Project slugs:** a new slug is auto-created, up to an org limit. An archived or over-limit slug returns 403; a malformed one returns 400.

## 4. Auto-instrumentation (TypeScript)

- **Anthropic / OpenAI SDK [PKG][GH].**
  - **What is bundled:** `raindrop-ai` bundles Traceloop instrumentations (v0.19, OTel v1) for OpenAI, Anthropic, Bedrock, Vertex, Cohere, LangChain, LlamaIndex, Pinecone, Qdrant, Chroma and Together.
  - **Default registration:** without `instrumentModules`, all of them are registered through require-hooks. These patch only modules loaded **after** `new Raindrop()` via CJS `require`.
  - **ESM (Node 22, `"type":"module"`, tsx/bundlers):** pass modules explicitly. The docs say Anthropic must be the **module namespace**:
    ```ts
    import * as AnthropicModule from "@anthropic-ai/sdk";
    import OpenAI from "openai";
    const raindrop = new Raindrop({ writeKey: process.env.RAINDROP_WRITE_KEY!, instrumentModules: { anthropic: AnthropicModule, openAI: OpenAI } });
    // then wrap calls: await interaction.withSpan({ name: "llm_generate" }, () => anthropic.messages.create({...}))
    ```
  - **What gets patched:** the Anthropic instrumentation patches `Anthropic.Messages.prototype.create` and `Completions.prototype.create`. Both still exist in `@anthropic-ai/sdk@0.133.0` [PKG]. `client.beta.*` calls are not covered **[UNVERIFIED end-to-end]**.
  - **Passing `instrumentModules` disables every default instrumentation you did not list.**
  - With an existing OTel/Sentry setup, use `useExternalOtel: true` plus `raindrop.createSpanProcessor()` and `raindrop.getInstrumentations()`. Use `raindrop-ai@otelv2` if the app is on OTel v2 [GH].
- **Vercel AI SDK [GH][PKG].**
  - `npm i @raindrop-ai/ai-sdk`
  - `const rd = createRaindropAISDK({ writeKey })`
  - `const { generateText, streamText } = rd.wrap(ai, { context: { userId, eventName }, selfDiagnostics: { enabled: true } })`
  - Per call: `experimental_telemetry: { isEnabled: true, metadata: eventMetadata({ userId, convoId, eventName, eventId, properties }) }`
  - Tools are traced automatically. Use `rd.signals.track({...})`, `rd.users.identify(...)`, `await rd.flush()` and `rd.shutdown()`.
  - With the core SDK only, use `import { metadata } from "raindrop-ai/otel"` for `experimental_telemetry.metadata`, or `interaction.vercelAiSdkMetadata()`.
- **Claude Agent SDK [GH].**
  - `npm i @raindrop-ai/claude-agent-sdk`
  - `const rd = createRaindropClaudeAgentSDK({ writeKey })`
  - `const { query } = rd.wrap(claudeAgentSDK, { selfDiagnostics: { enabled: true } })`
  - Call `query({prompt, options}, eventMetadata({ userId, eventName }))`. Only queries given `eventMetadata()` are tracked.
  - Finish with `await rd.flush()`.

## 5. Reading data back (for the RSI meta-agent)

### 5.1 Query API / `@raindrop-ai/query` (REST, read-only, beta) [PKG][TSC][DOCS-S]

- **Server:** `https://query.raindrop.ai`.
- **Auth:** `Authorization: Bearer <Query API key>`.
- **Project:** `X-Raindrop-Project-Id: <slug>`, set by the SDK option `projectId`.
- **Every endpoint is GET.** Pagination uses `cursor` / `meta.hasMore`; there is no bulk export endpoint.
- **Rate limits [DOCS-S]:** 200 RPM on most endpoints, 50 RPM on `/v1/events/search`, and 20 RPS overall. `events.search` date ranges are limited to 14 days.

| SDK call | REST | Key params |
|---|---|---|
| `events.list` | `/v1/events` | `limit, cursor, orderBy, timestamp{gte,gt,lte,lt}, userId, convoId, eventName (string or {eq,neq,startsWith,endsWith,contains}), signal (signal UUID), signalGroup, properties{key: v or {eq,neq,gt,gte,lt,lte}}, traits` |
| `events.get` | `/v1/events/{id}` | `id` |
| `events.search` | `/v1/events/search` | `query, mode: "text"\|"semantic"\|"regex", searchIn, signal, userId, convoId, threshold, limit, cursor, timestampGte, timestampLt` |
| `events.count` | `/v1/events/count` | Same filters as list, plus `countBy` (distinct users/convos) and `signalGroup` (union) |
| `events.timeseries` | `/v1/events/timeseries` | Filters plus `interval` |
| `events.facets` | `/v1/events/facets` | `field: "event_name"\|"user_id"\|"signal"`, `countBy, limit` |
| `traces.list` | `/v1/traces?event_id=` | `eventId` (required), `limit, truncLen` |
| `signals.list` / `signals.get` | `/v1/signals[/{id}]` | |
| `signalGroups.list` / `get` / `listSignals` | `/v1/signal-groups[/{id}[/signals]]` | |
| `users.list` / `get`, `conversations.list` / `get` | `/v1/users`, `/v1/conversations` | |

**Response shapes:**

- **Event:**
  - `{ id, eventName, userId, convoId, timestamp, receivedAt, userInput, assistantOutput, model, topics, featureFlags, properties, relevanceScore }`
  - `inputAttachments` / `outputAttachments`: `[{ attachmentId, attachmentType, name, value }]`
  - `signals`: `[{ id, name, score }]`
  - **`errorSpans`**: `[{ spanId, startedAt, status, durationMs, spanType, spanName, outputPayload }]`
  - **`toolCalls`**: `[{ toolName, status: OK|ERROR|UNSET, durationMs, startedAt, spanId }]`
  - Signals, errorSpans and toolCalls "may be absent for very recent events".
- **Trace span:** `{ traceId, spanId, parentSpanId, spanName, spanType: INTERNAL|LLM_GENERATION|LLM_GENERATION_STREAM|TOOL_CALL, status, startTimeNs, endTimeNs, durationNs, input, output, inputTokens, outputTokens, model, provider, attributes }`.
- **Signal:** `{ id, type: topic|regex|instrumented|metric|code, name, description, createdAt, groupId, groupName, sentiment: NEGATIVE|POSITIVE|NEUTRAL }`.

```ts
import { RaindropQuery } from "@raindrop-ai/query";
import * as errors from "@raindrop-ai/query/models/errors";
const rq = new RaindropQuery({ apiKey: process.env.RAINDROP_QUERY_API_KEY!, projectId: process.env.RAINDROP_PROJECT_ID ?? "default" });

const ev = await rq.events.get({ id: eventId });                     // ev.data.errorSpans / toolCalls / signals
const spans = await rq.traces.list({ eventId, limit: 200 });
const failed = spans.data.filter((s) => s.status === "ERROR");
const sig = (await rq.signals.list({ limit: 100 })).data.find((s) => s.name === "sim_tests_failed");
const recent = sig && await rq.events.list({ signal: sig.id, eventName: "plc_job",
  timestamp: { gte: new Date(Date.now() - 864e5) }, limit: 50 });
const hits = await rq.events.search({ query: "timer TON preset never elapses", mode: "semantic", limit: 20 });
// errors: catch (e) { if (e instanceof errors.RaindropQueryError) console.log(e.statusCode, e.body) }
```

**The Query API has NO issues, stumbles or triage endpoints.** Those are available only through MCP (5.2).

### 5.2 MCP tools (hosted server `https://mcp.raindrop.ai/mcp`) [GH][DOCS-S]

- **Auth:** OAuth 2.1, or `Authorization: Bearer <Query API key>`.
- **Write tools need scopes:** `write:issues`, `write:datasets`, `write:memories`, `write:signals` or `write:experiments`. API-key callers get them.
- **Project:** most read tools take `project` (a slug, or `"*"` org-wide on list/search/count tools). `get_event`, `get_trace`, `list_events` and `get_conversation` require a concrete project.
- **Time ranges:** `period` strings such as `"24h"` or `"7d"`.
- **Tool naming:** the docs list unprefixed names. The skills reference shows `raindrop_`-prefixed names (it says "`raindrop_query_cost` (`query_cost` on the server)"). **Call `tools/list` to confirm.** In Claude Code they appear as `mcp__raindrop__<name>`.

### 5.4 Evals (SDK eval mode) [PKG][TSC]

```ts
import { Raindrop, defineDataset, defineEvalSuite, defineLocalEvaluator, runEvalSuite, compareEvalRuns } from "raindrop-ai";
```

## 8. Built-in diagnosis features: what they are and how failures get grouped

- **Signals** [DOCS-S][PKG]
  - A signal is a named behavior tracked across every event, with rates over time.
  - Sources:
    - (a) *Created*: you describe a behavior in natural language; Raindrop drafts a classifier, runs it on a sample of real events, and you refine it with labeled examples. These count against "signal slots".
    - (b) *Regex*.
    - (c) *Instrumented*: from the SDK's `trackSignal`/`selfDiagnose`. No slot.
    - (d) *Presets*: for example user frustration, refusals, tool errors and context loss. No slot.
  - Query API types: `topic|regex|instrumented|metric|code`. Signals are grouped by sentiment and into signal groups.
- **Issues ("Issue Detection")** [GH][DOCS-S]
  - AI-generated investigation reports of broad shifts in the event distribution. Examples: a tool's error rate climbing, a model overrepresented in failures, a topic spiking.
  - Each report includes the affected dimensions (overrepresented tools, models and signals), a timeline and related events.
  - Ranked by severity and users affected. An issue can be turned into a persistent signal, and resolved, ignored or reopened via `update_issue`.
  - The Raindrop 2.0 post describes issues as "the same stumble recurring across many runs and users".
  - **The exact clustering algorithm is not documented [UNVERIFIED].** A third-party talk summary mentions embedding-based semantic clustering.
- **Stumbles** [GH][DOCS-S]
  - One-off bad experiences in a single interaction, including ones the agent reports about itself.
  - Scanned on a cadence, so they are not real-time.
  - Disjoint from issues: check both (`list_issues` and `search_stumbles`).
- **Triage Agent** [DOCS-S]
  - An investigation agent available in Slack, the web app and MCP (`ask_agent_question`).
  - Analyzes traces, signals and feedback. Returns root-cause hypotheses with supporting events, and keeps memory across follow-ups.
  - The docs warn that AI-generated analyses may be inaccurate.
- **Deep Search** [DOCS-S, partial]
  - Marketed as "Deep Research for your production AI data": search a topic and Raindrop trains small classifiers across millions of events (Gemini 2.5 Flash is used for categorization and query rewriting, per Google case study).
  - In current docs and APIs this shows up as semantic search (`search_events` / `events.search` with `mode: "semantic"`), natural-language signal creation, and NL trace search in Trajectories.
  - No standalone current docs page found **[UNVERIFIED as a separate API]**.
- **Self Diagnostics** [PKG][DOCS-S]
  - The agent calls `__raindrop_report` or you call `selfDiagnose`. This produces `type: "agent"` signals.
  - Shown in their own dashboard section, and they feed issue discovery.
- **Alerts** [DOCS-S]
  - Slack only, managed under Settings → Notifications.
  - *Signal Alerts*: a threshold on users or events affected, or every match; can be snoozed.
  - *Daily Digest*.
  - *Agent Briefs*: scheduled Triage investigations with a prompt, schedule and channel.
- **Experiments** [DOCS-S]
  - Compares two cohorts of already-logged events (Baseline vs Experiment). Each side is defined by date range plus conditions: model, feature flag, property, tool.
  - Outcome is all signals or the ones you pick. Measured as Events % or Users %, plus median cost per event.
  - It reads existing traffic and does not split or replay it. **Tag MongoMation events with `featureFlags`/`properties` such as `harness_version` so harness iterations can be compared.**
  - Third-party sources claim 95% CIs and p-values, and that it requires the Pro plan **[UNVERIFIED]**.
- **Evals:** see 5.4, plus Workshop's local "self-healing eval loop".
- **Other features:**
  - *Trajectories*: agent-run visualization, NL trace search, AI summary.
  - *Datasets*: saved events and traces with labels.
  - *Cost tracking*: the `usage` field on `trackAi`/`finish`, plus `query_cost`.

## 9. Suggested wiring for MongoMation

- **One Raindrop event per job attempt.**
  - `event` is `"plc_generate"`, `"plc_repair"` or `"meta_harness_iteration"`.
  - `convoId = jobId`, so all attempts of a job thread together.
  - `userId` = the requesting engineer or plant/line ID, used consistently. Never empty, since empty drops the event.
- **Tools:** name them consistently, for example `compile_plc`, `deploy_plc`, `run_simulation`, `repair_patch`. Record every failure with `startToolSpan().setError()` or `trackTool({ error })`.
- **Attachments:** ST source, the repair diff, and truncated compiler or simulator logs.
- **Properties and feature flags:**
  - Properties: `job_id`, `attempt`, `harness_version`, `tests_total`, `tests_failed`.
  - Feature flags: `harness_version`, `repair_strategy`.
- **Instrumented signals:** `compile_failed`, `deploy_failed`, `sim_tests_failed`, `eval_score`, and `selfDiagnose` for "stuck" states.
- **Mongo evidence doc:**
  `{ jobId, attempt, harnessVersion, raindrop: { eventId, eventName, convoId, projectId }, status, signals: [...], createdAt }`
  - Write it *before* `begin()` so the evidence exists even if the process crashes.
- **RSI loop:**
  1. Map signal names to UUIDs: `signals.list`.
  2. Pull failing events: `events.list({ signal, properties: { harness_version }, timestamp })`.
  3. Drill in with `events.get` (errorSpans, toolCalls) and `traces.list` (filter `status === "ERROR"`).
  4. Get clustered problems from MCP: `list_issues`, `get_issue_events`, `search_stumbles`.
  5. Store the evidence in Mongo.
  6. Change the harness, then `runEvalSuite` and `compareEvalRuns`. Or compare harness versions in Experiments.
  7. Poll with delays, because enrichment such as signals and errorSpans is asynchronous.

## 10. Caveats (top 10 first)

1. **raindrop.ai is not Raindrop.io.**
   - `raindrop-mcp`, `raindrop-cli` and `api.raindrop.io` belong to a bookmark app.
   - Use only `raindrop-ai` / `@raindrop-ai/*` packages and the `api.`, `query.` and `mcp.raindrop.ai` hosts.
2. **Two credentials.**
   - The write key handles ingest (`writeKey`, `api.raindrop.ai`).
   - The Query API key handles reads, MCP API-key auth and evals (`query.raindrop.ai`, `mcp.raindrop.ai`, `new Raindrop({ apiKey })`).
   - The TS SDK does not read `RAINDROP_WRITE_KEY` from the environment; pass it explicitly.
3. **Everything is buffered.**
   - `trackAi`/`trackSignal`/`setUserDetails` are synchronous and batched every 1 s.
   - `begin()` partials flush after 2 s idle.
   - Short-lived scripts must `await interaction.finish()` and `await raindrop.close()` (10 s deadline), or data is lost.
4. **`withTool`/`withSpan` do not mark a thrown error as a failed span in default mode.** Use `startToolSpan().setError()`, `trackTool({ error })`, or `bypassOtelForTools: true`.
5. **Event IDs.**
   - `begin()` requires `eventId` in its TS type, so pre-generate it with `randomUUID()` and store it.
   - `trackAi` returns `string | (string|undefined)[] | undefined`; `undefined` means it was rejected.
6. **Silent drops on validation.**
   - The schemas are strict: no unknown top-level keys, `userId` and `event` must be non-empty, and `trackAi` needs input or output.
   - Failures produce only a `console.warn`.
   - Span and tool `properties` must be `Record<string,string>`; event properties accept nested JSON.
7. **Always `finish()` with a non-empty `output`, even for failures.** A run with no output may produce no event. Failure status comes from errored spans, not from the output text.
8. **Size limits.** 1 MB per event, 1,000,000 chars per text field by default, and attachments count. Truncate logs and diffs.
9. **The read side is limited.**
   - The Query API is beta and read-only: 200 RPM, 50 RPM for search, 20 RPS overall, 14-day search ranges.
   - It has no issues or stumbles; those need MCP (`list_issues` needs the `new_issues_nav` flag).
   - MCP RQL is capped at 7-day windows.
   - Recent events may lack signals, errorSpans and toolCalls, and stumbles run on a cadence.
10. **Auto-instrumentation is fragile in ESM.**
    - Pass `instrumentModules` (Anthropic as `import * as`). Listing modules disables every unlisted default.
    - The bundled Traceloop instrumentations are OTel v1; use `raindrop-ai@otelv2` with OTel v2 apps.
    - The tracing pipeline is a per-process singleton: use one write key per process.

More caveats:

- **JSDoc examples inside the package are stale.** They show `interaction.end()`, `withWorkflow`/`withTask`, `addAttachment` (singular) and `withSpan("name", fn)`. Use the typed API shown above.
- **`setError(err)` needs a narrowed type** under `strict`, because `catch` variables are `unknown`.
- **`trackSignal` returns `void`**; awaiting it is pointless. Set `sentiment` explicitly.
- **MCP tool names** may or may not carry a `raindrop_` prefix depending on the source. Discover them with `tools/list`.
- **Dashboards over MCP** need OAuth (`write:dashboards`); API keys can only read them.
- **Workshop mirroring** auto-enables when `NODE_ENV=development`, which sends POSTs to `localhost:5899`. Set `localWorkshopUrl: false` in CI.
- **Proxies:** Node 22's built-in `fetch`, which the SDK uses, ignores `HTTPS_PROXY` unless `NODE_USE_ENV_PROXY=1` (Node ≥22.21). This matters behind corporate proxies.
- **Releases move fast.** `raindrop-ai` 1.0.0 shipped 2026-10-08 and 1.0.1 on 2026-10-09; pin exact versions. The Query SDK is beta, so pin it too.
- **Next.js:** add `raindrop-ai` to `serverExternalPackages`.
